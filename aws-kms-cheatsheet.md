## 1. Fundamentals and Mental Model

### Overview

AWS Key Management Service (KMS) manages cryptographic keys and provides controlled cryptographic operations. Applications use it to protect data keys (envelope encryption), while bulk data is encrypted locally or by integrated AWS services. KMS is not a secret-value database — use Secrets Manager for application secrets, with KMS protecting the encryption keys underneath.

### Core Concepts

| Component | Description |
|-----------|-------------|
| **KMS Key** | Logical container for key material. Never leaves KMS. |
| **Data Key** | AES-256 key generated by KMS, used to encrypt bulk data locally. |
| **Key Policy** | Resource-based policy attached to every KMS key; mandatory. |
| **Alias** | Friendly name for a key (e.g., `alias/orders`). Does not identify a specific version. |
| **Key ARN** | Immutable identifier for the key resource. |
| **Encryption Context** | Non-secret AAD (additional authenticated data) that binds ciphertext to its context. |
| **Grant** | Delegated, time-scoped usage permission — used extensively by AWS services. |

### Mental Model: KMS is a Gatekeeper, Not a Vault

```
KMS = Gatekeeper for cryptographic operations
├── Your data NEVER enters KMS (except <4 KB direct Encrypt calls)
├── KMS generates and wraps data keys
├── Your application encrypts bulk data locally with the data key
└── KMS controls WHO can unwrap (decrypt) the data key

Authorization layers:
  KMS Key Policy  ← primary gate (must exist)
  IAM Policy      ← secondary gate (if key policy delegates to IAM)
  Grants          ← delegated gate (used by AWS services)
```

### Full Envelope Encryption Lifecycle (ASCII Diagram)

```
ENCRYPT FLOW
─────────────────────────────────────────────────────────────────────
  Application
      │
      │  1. GenerateDataKey(KeyId, EncryptionContext)
      ▼
  ┌─────────┐
  │   KMS   │  ── checks key policy + IAM policy ──►  ALLOW / DENY
  └─────────┘
      │
      │  Returns:
      │   ├── PlaintextDataKey  (AES-256, in memory only)
      │   └── EncryptedDataKey  (wrapped by KMS key, safe to store)
      ▼
  Application (in memory)
      │
      │  2. Encrypt bulk data with PlaintextDataKey
      │     using AES-GCM via local library (e.g., cryptography, boto3 is not used here)
      ▼
      │  3. Immediately DISCARD PlaintextDataKey from memory
      │
      │  4. STORE together:
      │     ├── Encrypted data (ciphertext)
      │     └── EncryptedDataKey
      │     (and EncryptionContext metadata — for context verification on decrypt)
      ▼
  Storage (S3, database, disk)

─────────────────────────────────────────────────────────────────────
DECRYPT FLOW
─────────────────────────────────────────────────────────────────────
  Application reads from storage:
      │  EncryptedData + EncryptedDataKey + EncryptionContext
      │
      │  1. Decrypt(EncryptedDataKey, EncryptionContext)
      ▼
  ┌─────────┐
  │   KMS   │  ── checks key policy + IAM + context match ──► ALLOW / DENY
  └─────────┘
      │
      │  Returns: PlaintextDataKey (in memory only)
      ▼
  Application
      │
      │  2. Decrypt bulk data with PlaintextDataKey
      │
      │  3. Discard PlaintextDataKey from memory
      ▼
  Plaintext data returned to caller
─────────────────────────────────────────────────────────────────────
```

### Detailed Envelope Encryption Flow with Components

```
┌────────────────────────────────────────────────────────────────────┐
│                    ENVELOPE ENCRYPTION ARCHITECTURE                 │
└────────────────────────────────────────────────────────────────────┘

Layer 1: KMS Key (Master Key)
┌─────────────────────────────────────┐
│  KMS Key (SYMMETRIC_DEFAULT)        │
│  ├── Key Material (256-bit AES)     │  ← Never leaves KMS
│  ├── Key Policy (authorization)     │  ← Controls who can use
│  ├── Automatic Rotation (optional)  │  ← New material, same ID
│  └── CloudTrail Logging            │  ← Every operation logged
└─────────────────────────────────────┘
           │
           │ Generates & Wraps
           ▼
Layer 2: Data Key (Envelope Key)
┌─────────────────────────────────────┐
│  Data Key (AES-256)                 │
│  ├── Plaintext Form                 │  ← Used in memory only
│  ├── Encrypted Form (wrapped)       │  ← Stored with ciphertext
│  └── Unique per operation           │  ← New key each time
└─────────────────────────────────────┘
           │
           │ Encrypts
           ▼
Layer 3: Data (Bulk Content)
┌─────────────────────────────────────┐
│  Your Application Data              │
│  ├── S3 Objects (GB to TB)          │
│  ├── Database Records               │
│  ├── EBS Volumes                    │
│  └── Files on Disk                  │
└─────────────────────────────────────┘

WHY THIS ARCHITECTURE?
├── Performance: Encrypt locally (fast) instead of via API (slow)
├── Scale: No 4 KB KMS limit on bulk data
├── Cost: One KMS call per file/object instead of per byte
├── Security: KMS key material never leaves hardware boundaries
└── Compliance: Centralized key governance, distributed encryption

STORED TOGETHER:
┌────────────────────────────────────┐
│  Encrypted Data + Encrypted Key    │  ← Both stored together
│  + EncryptionContext (metadata)    │  ← Context for verification
└────────────────────────────────────┘
```

### Security Properties of Envelope Encryption

| Property | How It's Achieved |
|----------|------------------|
| **Key material isolation** | KMS keys never leave FIPS 140-2 validated hardware |
| **Least privilege per layer** | KMS key policy separate from application permissions |
| **Defense in depth** | Compromise requires: (1) access to encrypted data, (2) access to KMS Decrypt API |
| **Audit trail** | Every GenerateDataKey/Decrypt logged in CloudTrail with principal, context, timestamp |
| **Context binding** | EncryptionContext AAD prevents ciphertext from being used in wrong context |
| **No key reuse risk** | Each data encryption uses a fresh data key |
| **Automatic rotation** | Rotating KMS key doesn't require re-encrypting bulk data |

### KMS vs Secrets Manager

| Question | KMS | Secrets Manager |
|----------|-----|----------------|
| What does it store? | Cryptographic key material | Secret values (passwords, tokens, API keys) |
| Primary operation | Encrypt/Decrypt/GenerateDataKey | GetSecretValue, automatic rotation |
| Rotation | Rotates key material; does NOT re-encrypt data | Rotates the actual secret value via Lambda |
| Cost model | Per-API call + per-key/month | Per-secret/month + per API call |
| When to use | Control who can decrypt data | Store and rotate application credentials |

## 2. Key Ownership and Control

### Key Types Comparison

| Type | Where / Control | Rotation | Cost | Cross-Account | Typical Reason |
|------|----------------|----------|------|---------------|----------------|
| **Customer managed** | Your account; you control policy/lifecycle | Configurable (90–2560 days) or on-demand | $1/mo + API calls | Yes, with key policy | Audit, separation of duties, cross-account |
| **AWS managed** | Your account; AWS controls policy | Automatic (every year, cannot disable) | Free | No | Service-integrated encryption with less admin |
| **AWS owned** | AWS-owned service account | AWS managed | Free | No | Transparent service encryption |

AWS managed keys generally cannot enable the cross-account encrypted-resource sharing that requires a customer managed key. Key existence, usage costs, and audit visibility differ by ownership type.

### Key Specifications

| Spec | Usage | Algorithm |
|------|-------|-----------|
| `SYMMETRIC_DEFAULT` | Encrypt/Decrypt | AES-256-GCM |
| `RSA_2048 / 4096` | Asymmetric encrypt or sign | RSA-OAEP / RSASSA-PSS |
| `ECC_NIST_P256 / P384 / P521` | Sign/Verify only | ECDSA |
| `HMAC_256 / 384 / 512` | MAC generation/verification | HMAC |
| `SM2 / SM4` | China regions only | OSCCA algorithms |

A signing key is not interchangeable with an encryption key — AWS enforces key usage (ENCRYPT_DECRYPT vs SIGN_VERIFY) at creation time.

### Default Key Policy vs Custom Key Policy

**Default key policy** (created by the KMS console or CLI without specifying a policy):
- Contains a single `EnableRootAccountPermissions` statement granting `kms:*` to the account root.
- This means IAM policies in that account can control access to the key — the key is fully IAM-delegated.
- Useful as a starting point but should be locked down for production.

**Custom key policy**:
- You supply all statements explicitly.
- If you omit the root account trust statement, IAM policies in your account have no effect on the key.
- Key administrators and key users are defined explicitly with least-privilege actions.
- Required when you need cross-account access, grant restrictions, or separation of admin vs user.

### What Happens If You Lock Yourself Out of a Key

If you create a key with a policy that grants access to no valid principal (e.g., deletes the root trust statement and references a non-existent role), **no one in your account can manage or use the key**. There is no self-service recovery mechanism.

- You cannot view, modify, or delete the key policy via the console or API.
- You must contact **AWS Support** to regain access.
- AWS Support can help restore the default key policy, but this requires identity verification through your account's root user or support contact.
- This is not fast — plan carefully before modifying key policies, especially removing the root trust.

> **Prevention:** Always test key policy changes in a staging environment. Keep the `EnableRootAccountPermissions` statement unless you have a deliberate reason to remove it.

## 3. Envelope Encryption Step by Step

### Why Envelope Encryption?

The KMS `Encrypt` API accepts at most **4,096 bytes** of plaintext. This is by design — KMS is optimized for protecting cryptographic keys, not bulk data. Sending gigabytes of data to KMS would be:
- Slow (every byte crosses the network to KMS)
- Expensive (charged per API call)
- Against the threat model (keys should never leave the hardware)

Instead, KMS issues a **data key** that your application uses locally. Only the small (32-byte) data key is protected by KMS. Services like S3 and RDS use envelope encryption under the hood via their service integrations — they never send object data to KMS.

### Python boto3: Envelope Encryption (Encrypt)

```python
import boto3
import os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

def encrypt_data(plaintext: bytes, kms_key_id: str, encryption_context: dict) -> dict:
    """
    Encrypt plaintext using KMS envelope encryption.
    Returns a dict with encrypted_data, encrypted_data_key, and nonce.
    """
    kms = boto3.client("kms", region_name="us-east-1")

    # Step 1: Request a data key from KMS
    response = kms.generate_data_key(
        KeyId=kms_key_id,
        KeySpec="AES_256",
        EncryptionContext=encryption_context,
    )

    plaintext_data_key = response["Plaintext"]      # bytes – use immediately
    encrypted_data_key = response["CiphertextBlob"] # bytes – safe to store

    # Step 2: Encrypt bulk data locally using AES-256-GCM
    nonce = os.urandom(12)                           # 96-bit nonce for GCM
    aesgcm = AESGCM(plaintext_data_key)
    encrypted_data = aesgcm.encrypt(nonce, plaintext, None)

    # Step 3: Discard the plaintext data key immediately
    del plaintext_data_key

    # Step 4: Store ciphertext + encrypted data key + nonce together
    return {
        "encrypted_data": encrypted_data,
        "encrypted_data_key": encrypted_data_key,
        "nonce": nonce,
        "encryption_context": encryption_context,   # store for decryption
    }

# Usage
result = encrypt_data(
    plaintext=b"sensitive customer record",
    kms_key_id="alias/my-app-key",
    encryption_context={"application": "orders", "environment": "production"},
)
```

### Python boto3: Envelope Decryption (Decrypt)

```python
import boto3
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

def decrypt_data(encrypted_payload: dict) -> bytes:
    """
    Decrypt data encrypted with envelope encryption.
    encrypted_payload must contain: encrypted_data, encrypted_data_key,
    nonce, and encryption_context.
    """
    kms = boto3.client("kms", region_name="us-east-1")

    # Step 1: Ask KMS to unwrap the data key
    # The EncryptionContext MUST match what was used during GenerateDataKey
    response = kms.decrypt(
        CiphertextBlob=encrypted_payload["encrypted_data_key"],
        EncryptionContext=encrypted_payload["encryption_context"],
    )

    plaintext_data_key = response["Plaintext"]  # bytes – use immediately

    # Step 2: Decrypt bulk data locally
    aesgcm = AESGCM(plaintext_data_key)
    plaintext = aesgcm.decrypt(
        encrypted_payload["nonce"],
        encrypted_payload["encrypted_data"],
        None,
    )

    # Step 3: Discard the plaintext data key
    del plaintext_data_key

    return plaintext

# Usage
plaintext = decrypt_data(result)
print(plaintext)  # b"sensitive customer record"
```

### Key Points

- `generate_data_key` returns both plaintext and ciphertext forms of the data key.
- The plaintext form is used **only in memory** for the duration of the encryption operation.
- KMS never sees your bulk data — only the data key is communicated to KMS.
- For decryption, you pass only the `EncryptedDataKey` back to KMS — KMS does not need to know about your actual data.
- You must pass the **same EncryptionContext** during decryption that was used during generation. Omitting it is one of the most common KMS bugs.

## 4. Authorization: Key Policy, IAM Policy, Grants

### Authorization Mechanisms

| Mechanism | Purpose | Notes |
|-----------|---------|-------|
| **Key policy** | Resource-based policy, primary gate for every key | Every key has exactly one; max 32 KB |
| **IAM policy** | Principal permissions — only effective if key policy allows IAM delegation | Must not be the sole authorization mechanism |
| **Grant** | Delegated, constrained key usage; often for AWS service integrations | CreateGrant API; retired via RevokeGrant |
| **SCP / Permissions Boundary / Explicit Deny** | Additional effective-permission restrictions | Can reduce but not expand permissions |

### The Critical "Key Policy Must Allow" Rule

> **Without an explicit account-level trust statement in the key policy, IAM policies alone are insufficient to grant access to a KMS key.**

This is the single most-tested KMS authorization concept:

```
IAM POLICY alone = NOT ENOUGH
Key Policy + IAM Policy = Full access path (for same-account principals)
Key Policy alone = Sufficient (principal listed directly in key policy)
```

If the key policy contains the root account trust (`"Principal": {"AWS": "arn:aws:iam::ACCOUNT:root"}`), then IAM policies can be used to control access just like any other resource. If that statement is absent, IAM policies have no effect on that key — even for account administrators.

### Full Key Policy JSON (Revisited with Context)

See Section 2 for the complete example. The statement structure to remember:

| Statement | Actions Granted | Who Gets It |
|-----------|----------------|-------------|
| `EnableRootAccountPermissions` | `kms:*` | Account root — enables IAM delegation |
| `AllowKeyAdministrators` | Lifecycle management actions | Ops/security roles |
| `AllowKeyUsers` | Cryptographic operations | Application roles |
| `AllowCrossAccountAccess` | Decrypt + GenerateDataKey | External account root |

### IAM Policy Granting Key Usage

The following IAM policy allows a role to perform cryptographic operations on a specific key. This is effective only if the key policy has the root trust statement:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowKMSKeyUsage",
      "Effect": "Allow",
      "Action": [
        "kms:Encrypt",
        "kms:Decrypt",
        "kms:ReEncrypt*",
        "kms:GenerateDataKey*",
        "kms:DescribeKey"
      ],
      "Resource": "arn:aws:kms:us-east-1:123456789012:key/mrk-1234abcd12ab34cd56ef1234567890ab"
    }
  ]
}
```

### Grants: Delegated Key Usage

Grants are used when an AWS service (e.g., EBS, ECS, Redshift) needs temporary, constrained access to a key on behalf of a principal. They avoid the overhead of modifying the key policy for every service call.

```bash
# Create a grant allowing an EC2 Auto Scaling role to generate data keys
aws kms create-grant \
  --key-id alias/my-app-key \
  --grantee-principal arn:aws:iam::123456789012:role/aws-service-role/autoscaling.amazonaws.com/AWSServiceRoleForAutoScaling \
  --operations GenerateDataKeyWithoutPlaintext Decrypt CreateGrant \
  --name "AutoScalingGrant"
```

```bash
# List grants on a key
aws kms list-grants --key-id alias/my-app-key

# Revoke a grant
aws kms revoke-grant \
  --key-id alias/my-app-key \
  --grant-id <grant-id-from-list-grants>
```

Key properties of grants:
- Grants can be further delegated (if `CreateGrant` is included in operations).
- Grants do not require key policy modification.
- Grants can have **grant constraints** such as `EncryptionContextEquals` to limit scope.
- AWS services create and retire grants automatically for service integrations (e.g., EBS volume encryption).

### Authorization Decision Tree

```
Request arrives at KMS
        │
        ├─ Is there an EXPLICIT DENY in the key policy? ──► DENY immediately
        │
        ├─ Is the principal listed directly in the key policy with Allow?
        │    └─ YES ──► Check for valid Grant or proceed to ──► ALLOW
        │
        ├─ Does the key policy have the root account trust statement?
        │    ├─ YES ──► Check caller's IAM policy for allow ──► ALLOW / DENY
        │    └─ NO  ──► IAM policies are irrelevant ──► DENY
        │
        └─ Does a valid Grant exist for this principal + operation?
             └─ YES ──► ALLOW (grants bypass key policy checks)
```

## 5. Encryption Context and Service Conditions

### What Is Encryption Context?

Encryption context is a set of non-secret key-value pairs that are cryptographically bound to ciphertext. It is additional authenticated data (AAD) used in AES-GCM. The same context must be provided on decryption — if any key or value differs, KMS returns `InvalidCiphertextException`.

- **Not encrypted** — context is visible in CloudTrail audit logs.
- **Not secret** — do not include passwords, tokens, or PII.
- **Immutable per ciphertext** — context is baked into the ciphertext; it cannot be changed after encryption.

### Request with Encryption Context

```json
{
  "KeyId": "alias/orders-key",
  "Plaintext": "<base64-encoded data>",
  "EncryptionContext": {
    "application": "orders-service",
    "environment": "production",
    "dataClassification": "PII",
    "tenant": "tenant-42"
  }
}
```

### Enforcing Encryption Context in a Key Policy

You can require that specific context values be present before KMS will perform an operation. This is especially useful for multi-tenant applications to prevent one tenant's principal from decrypting another tenant's data.

```json
{
  "Sid": "RequireEncryptionContext",
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::123456789012:role/AppServiceRole"
  },
  "Action": [
    "kms:Decrypt",
    "kms:GenerateDataKey"
  ],
  "Resource": "*",
  "Condition": {
    "StringEquals": {
      "kms:EncryptionContext:application": "orders-service",
      "kms:EncryptionContext:environment": "production"
    }
  }
}
```

With this policy, a caller that omits `environment=production` from the encryption context will receive `AccessDenied`, even if they have IAM permissions to use the key.

### kms:ViaService Condition

Restrict key usage to calls originating from a specific AWS service:

```json
{
  "Sid": "AllowS3SSEKMSOnly",
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::123456789012:role/AppServiceRole"
  },
  "Action": [
    "kms:GenerateDataKey",
    "kms:Decrypt"
  ],
  "Resource": "*",
  "Condition": {
    "StringEquals": {
      "kms:ViaService": "s3.us-east-1.amazonaws.com"
    }
  }
}
```

This means the key can only be used when the call originates from S3 in `us-east-1`. A direct `kms:Decrypt` API call from your application code would be denied.

### Common Mistake: Context Mismatch Between Encrypt and Decrypt

```
ENCRYPT call:
  EncryptionContext = { "application": "orders", "env": "prod" }
  ✅ Succeeds

DECRYPT call (common mistake):
  EncryptionContext = {}     ← omitted entirely
  ❌ Fails with InvalidCiphertextException

DECRYPT call (another common mistake):
  EncryptionContext = { "application": "orders" }   ← partial
  ❌ Fails with InvalidCiphertextException

DECRYPT call (correct):
  EncryptionContext = { "application": "orders", "env": "prod" }
  ✅ Succeeds
```

The error message `InvalidCiphertextException` is deliberately generic — KMS does not tell you whether the key ID, ciphertext, or context was wrong, to prevent information leakage to attackers.

## 6. Key Rotation

### Rotation Behavior by Key Type

| Key / Material Type | Automatic Rotation | On-Demand Rotation | Notes |
|---------------------|-------------------|-------------------|-------|
| Symmetric, `AWS_KMS` origin | Yes (90–2,560 days) | Yes | Default period is 365 days when enabled |
| Symmetric, `EXTERNAL` origin | No | Yes (as of 2023) | You supply new material for on-demand |
| Asymmetric (RSA, ECC) | No | No | Replace key (create new, re-point alias) |
| HMAC | No | No | Replace key manually |
| AWS managed keys | Yes (every ~365 days) | No | Managed by AWS; cannot be disabled |
| Custom key store (CloudHSM) | Yes (90–2,560 days) | Yes | HSM cluster must be healthy |

### CLI: Enable and Check Automatic Rotation

```bash
# Enable automatic rotation with default period (365 days)
aws kms enable-key-rotation \
  --key-id alias/my-app-key

# Enable automatic rotation with a custom period (180 days)
aws kms enable-key-rotation \
  --key-id alias/my-app-key \
  --rotation-period-in-days 180

# Check rotation status and next rotation date
aws kms get-key-rotation-status \
  --key-id alias/my-app-key

# Example response
{
    "KeyRotationEnabled": true,
    "KeyId": "1234abcd-12ab-34cd-56ef-1234567890ab",
    "RotationPeriodInDays": 180,
    "NextRotationDate": "2025-04-12T00:00:00+00:00",
    "OnDemandRotationStartDate": "2024-10-12T14:23:45+00:00"
}
```

### CLI: On-Demand Rotation

On-demand rotation lets you trigger an immediate rotation of the key material without waiting for the scheduled period. Use this when you suspect a key is compromised or need to rotate ahead of schedule.

```bash
# Trigger immediate rotation of key material
aws kms rotate-key-on-demand \
  --key-id alias/my-app-key

# List all rotations for a key (shows history of key material versions)
aws kms list-key-rotations \
  --key-id alias/my-app-key
```

### What Rotation Does (and Does Not Do)

```
ROTATION DOES:
├── Generate new cryptographic key material
├── Retain ALL previous key material versions (for decryption of old ciphertext)
├── Keep the same key ID, ARN, and aliases
└── New encryptions use the new key material automatically

ROTATION DOES NOT:
├── Re-encrypt any existing data (S3 objects, EBS snapshots, RDS volumes, etc.)
├── Rotate data keys that were already issued
├── Invalidate existing ciphertext
└── Change key policies, grants, or tags
```

**Mental model:** After rotation, KMS is like a key ring. New data uses the newest key on the ring. Old ciphertext can still be decrypted because KMS remembers all previous keys on the ring. The ring grows with each rotation.

### What to Do After Suspected Key Compromise

Rotation alone does not remediate a compromise of previously encrypted data. If you believe a key or its data keys have been compromised:

1. **Rotate the KMS key immediately** (on-demand rotation) — new encryptions use new material.
2. **Identify all data encrypted under the compromised key material version** using CloudTrail logs (filter by `KeyId` and `GenerateDataKey` events before the rotation date).
3. **Re-encrypt the data** using `ReEncrypt` API (server-side) or decrypt + re-encrypt (client-side) with the new key material or a new key entirely.
4. **Revoke grants** that may have allowed the compromised access path.
5. **Rotate or invalidate the IAM credentials** of the principal suspected of compromise.
6. **Consider disabling or deleting the key** if the compromise was severe — after re-encrypting all data.

```bash
# Re-encrypt a ciphertext blob from old key material to new key material
# (same key, new version, or different destination key)
aws kms re-encrypt \
  --ciphertext-blob fileb://encrypted-data-key.bin \
  --destination-key-id alias/my-app-key \
  --source-encryption-context '{"application":"orders"}' \
  --destination-encryption-context '{"application":"orders"}'
```

## 7. Multi-Region Keys

### Overview

Multi-Region keys have shared key material and key ID properties, allowing compatible cryptographic use across different AWS Regions. They are still **separate regional resources** with independent policies, grants, aliases, tags, and enabled state.

```
Multi-Region Primary Key (us-east-1)
  Key ARN: arn:aws:kms:us-east-1:123456789012:key/mrk-1234abcd...
  Key Policy: { ... }
  Aliases: alias/app-key
  State: Enabled
        │
        │ Replicate to
        ▼
Multi-Region Replica Key (eu-west-1)
  Key ARN: arn:aws:kms:eu-west-1:123456789012:key/mrk-1234abcd...
  Key Policy: { ... }  ← SEPARATE policy; NOT shared with primary
  Aliases: alias/app-key-eu  ← SEPARATE alias; NOT shared
  State: Enabled
```

**Key properties that ARE shared:** Key material and key ID prefix (`mrk-...`).
**Key properties that are NOT shared:** Key policy, grants, aliases, tags, enabled/disabled state, rotation settings.

### Use Cases

- Encrypt data in one Region, decrypt in another (e.g., DR, global active-active).
- Keep data encrypted in transit between Regions without decrypting and re-encrypting.
- Reduce latency by using a local replica key instead of calling a remote Region.

### Multi-Region Key Policy Gotcha

Each replica must have its own key policy explicitly configured. Replicating a key does **not** copy the source key policy. If you replicate a key and forget to configure its policy, the replica may use only the default policy (account root trust), which may be too permissive for your needs.

```bash
# Create a replica of a multi-region key
aws kms replicate-key \
  --key-id arn:aws:kms:us-east-1:123456789012:key/mrk-1234abcd12ab34cd56ef1234567890ab \
  --replica-region eu-west-1

# After replication, immediately set an appropriate key policy on the replica
aws kms put-key-policy \
  --key-id arn:aws:kms:eu-west-1:123456789012:key/mrk-1234abcd12ab34cd56ef1234567890ab \
  --policy-name default \
  --policy file://eu-west-1-key-policy.json
```

For imported material multi-Region keys, the material must be imported into each replica independently — KMS does not copy externally managed material between Regions.

## 8. Disable, Deletion, and Recoverability

### Key States and Allowed Operations

| State | Can Encrypt | Can Decrypt | Can Manage Policy | Notes |
|-------|------------|-------------|------------------|-------|
| **Enabled** | Yes | Yes | Yes | Normal operation |
| **Disabled** | No | No | Yes | Data is inaccessible; key exists |
| **Pending deletion** | No | No | No (limited) | 7–30 day window; cancelable |
| **Pending import** | No | No | Yes | Waiting for external key material |

Disabling a key **preserves** the key but immediately interrupts all encryption and decryption. Services using the key will fail. Use this to quickly halt key usage without deleting it — useful when investigating suspicious activity.

### Deletion Waiting Period

```bash
# Schedule key deletion (minimum 7 days, maximum 30 days)
aws kms schedule-key-deletion \
  --key-id alias/my-app-key \
  --pending-window-in-days 14

# Cancel deletion during the waiting period
aws kms cancel-key-deletion \
  --key-id 1234abcd-12ab-34cd-56ef-1234567890ab
```

The waiting period exists to prevent accidental data loss. Any access attempts during this period are logged in CloudTrail — if legitimate usage appears, you can cancel deletion before it's too late.

After deletion:
- The key is permanently gone.
- All data encrypted solely under this key becomes **permanently unrecoverable** — AWS cannot help.
- An alias with the same name does not recreate the old key material.
- Multi-Region primary deletion requires all replicas to be deleted first.

> **Treat key lifecycle as part of backup retention policy.** A retained database snapshot is useless if its encryption key has been deleted.

## 10. Common Patterns

### Pattern 1: S3 Server-Side Encryption with SSE-KMS (Customer Managed Key)

```bash
# Create a customer managed key for S3
aws kms create-key \
  --description "S3 bucket encryption key for orders data" \
  --key-usage ENCRYPT_DECRYPT \
  --key-spec SYMMETRIC_DEFAULT

# Create an alias
aws kms create-alias \
  --alias-name alias/s3-orders-key \
  --target-key-id <key-id-from-above>

# Enable Bucket Key (reduces KMS API calls and cost)
aws s3api put-bucket-encryption \
  --bucket my-orders-bucket \
  --server-side-encryption-configuration '{
    "Rules": [
      {
        "ApplyServerSideEncryptionByDefault": {
          "SSEAlgorithm": "aws:kms",
          "KMSMasterKeyID": "alias/s3-orders-key"
        },
        "BucketKeyEnabled": true
      }
    ]
  }'

# Upload an object with explicit SSE-KMS
aws s3api put-object \
  --bucket my-orders-bucket \
  --key orders/2024/record.json \
  --body record.json \
  --server-side-encryption aws:kms \
  --ssekms-key-id alias/s3-orders-key
```

**How S3 avoids the 4 KB limit:** S3 calls `GenerateDataKey` to get an AES-256 data key, encrypts each object locally with that key, and stores the encrypted data key as object metadata. S3 never sends object data to KMS.

### Pattern 2: Encrypting an RDS Database with a Customer Managed KMS Key

Encryption must be enabled at **creation time** — you cannot encrypt an existing unencrypted RDS instance in place.

```bash
# Create encrypted RDS instance with customer managed key
aws rds create-db-instance \
  --db-instance-identifier prod-orders-db \
  --db-instance-class db.t3.medium \
  --engine postgres \
  --master-username admin \
  --master-user-password <password> \
  --allocated-storage 100 \
  --storage-encrypted \
  --kms-key-id alias/rds-orders-key

# To encrypt an EXISTING unencrypted instance:
# 1. Create a manual snapshot of the unencrypted instance
aws rds create-db-snapshot \
  --db-instance-identifier my-unencrypted-db \
  --db-snapshot-identifier my-unencrypted-snapshot

# 2. Copy snapshot with encryption enabled
aws rds copy-db-snapshot \
  --source-db-snapshot-identifier my-unencrypted-snapshot \
  --target-db-snapshot-identifier my-encrypted-snapshot \
  --kms-key-id alias/rds-orders-key

# 3. Restore a new instance from the encrypted snapshot
aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier my-new-encrypted-db \
  --db-snapshot-identifier my-encrypted-snapshot
```

**Key points:**
- The KMS key must be in the same Region as the RDS instance.
- Read replicas in a different Region require a separate KMS key in that Region.
- Cross-account snapshot sharing requires the KMS key to be a customer managed key (AWS managed keys cannot be shared cross-account).

### Pattern 3: Cross-Account KMS Key Access

Two-step setup: the key policy in Account A must allow Account B, and Account B's IAM policy must allow the operation.

```
Account A (Key Owner): 111122223333
Account B (Key User):  444455556666
```

**Step 1: Account A — Add cross-account statement to key policy**

```json
{
  "Sid": "AllowCrossAccountUse",
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::444455556666:root"
  },
  "Action": [
    "kms:Decrypt",
    "kms:GenerateDataKey",
    "kms:DescribeKey",
    "kms:ReEncrypt*"
  ],
  "Resource": "*"
}
```

**Step 2: Account B — Attach IAM policy to role/user**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "kms:Decrypt",
        "kms:GenerateDataKey",
        "kms:DescribeKey"
      ],
      "Resource": "arn:aws:kms:us-east-1:111122223333:key/1234abcd-12ab-34cd-56ef-1234567890ab"
    }
  ]
}
```

**Step 3: Account B — Use the key**

```bash
# Generate a data key using Account A's key from Account B
aws kms generate-data-key \
  --key-id arn:aws:kms:us-east-1:111122223333:key/1234abcd-12ab-34cd-56ef-1234567890ab \
  --key-spec AES_256
```

**Note:** AWS managed keys in Account A cannot be used cross-account. Only customer managed keys support cross-account access.

### Pattern 4: KMS Envelope Encryption in Application Code

See Section 3 for the full Python boto3 code examples. The conceptual pattern applies to any SDK:

```
Application                KMS                 Local Crypto Library
     │                      │                        │
     │── GenerateDataKey ───►│                        │
     │◄── PlaintextKey ──────│                        │
     │◄── EncryptedKey ──────│                        │
     │                      │                        │
     │── encrypt(data, PlaintextKey) ────────────────►│
     │◄── ciphertext ────────────────────────────────│
     │                      │                        │
     │  discard PlaintextKey from memory              │
     │                      │                        │
     │  store(ciphertext + EncryptedKey)              │
     │                      │                        │
     ├─── DECRYPT FLOW ────────────────────────────── │
     │                      │                        │
     │── Decrypt(EncryptedKey) ─────────────────────►│
     │◄── PlaintextKey ──────│                        │
     │                      │                        │
     │── decrypt(ciphertext, PlaintextKey) ──────────►│
     │◄── plaintext ─────────────────────────────────│
```

## 11. Troubleshooting and Practical Inspection

### Error Reference

| Error / Symptom | Root Causes | Resolution |
|-----------------|-------------|------------|
| `AccessDeniedException` on `Decrypt` | 1. Caller not in key policy<br>2. Key policy has no root trust + IAM policy is insufficient<br>3. Explicit deny in key policy or SCP<br>4. `kms:ViaService` condition not met (call isn't from expected service)<br>5. Encryption context mismatch triggers policy condition | Check key policy, IAM policy, grants; verify context and ViaService conditions |
| `AccessDeniedException` on `GenerateDataKey` | 1. IAM role lacks `kms:GenerateDataKey` permission<br>2. Key policy does not allow the role<br>3. `kms:EncryptionContext` condition in key policy not satisfied | Verify role ARN is in key policy; verify encryption context |
| `InvalidCiphertextException` | 1. EncryptionContext on decrypt does not match encrypt<br>2. Ciphertext corrupted or truncated in storage<br>3. Ciphertext decrypted with wrong key<br>4. Ciphertext from different algorithm/region | Verify context keys and values are byte-for-byte identical; check storage integrity |
| `NotFoundException` | 1. Key ID or alias does not exist in the Region<br>2. Alias points to deleted key<br>3. Calling wrong Region | Use `describe-key` to verify key exists; check Region in ARN |
| `DisabledException` | Key is in Disabled state | Re-enable key: `aws kms enable-key --key-id <id>` |
| `KMSInvalidStateException` | Key is in Pending Deletion or Pending Import state | Cancel deletion or complete import |
| `ThrottlingException` | Request rate exceeds quota for key/Region | Implement exponential backoff; use data key caching; request quota increase |
| Cross-account S3 read fails | 1. S3 object encrypted with customer managed key from owner account<br>2. Cross-account caller's IAM policy does not reference the foreign key ARN<br>3. Key policy does not allow the cross-account principal | Add cross-account statement to key policy; add IAM policy in caller account |
| Old data fails after alias change | Ciphertext embedded key ID (or ARN) it was encrypted under; changing alias target does not re-encrypt old data | Keep old key active; use `ReEncrypt` to migrate ciphertext to new key |
| Lambda decryption fails after role update | IAM role was re-created with new ARN; old ARN is still in key policy | Update key policy `AllowKeyUsers` statement with new role ARN |

## 13. Exam Tips Summary

### Must-Know Concepts

1. **Key policy is mandatory and primary.** Every KMS key has exactly one key policy. Without the root account trust statement, IAM policies have no effect on the key.

2. **Envelope encryption — KMS never sees bulk data.** `GenerateDataKey` returns both plaintext and encrypted forms. Bulk data is encrypted locally; KMS only protects the 32-byte data key.

3. **KMS `Encrypt` API limit is 4 KB.** This is for direct encryption of small values (passwords, data keys). Services like S3/RDS avoid this via envelope encryption.

4. **Rotation does NOT re-encrypt existing data.** It generates new key material for future encryptions; old ciphertext is still decryptable via retained prior material. Remediating a compromise requires explicit re-encryption.

5. **AWS managed keys rotate automatically; customer managed keys do not by default.** Automatic rotation must be explicitly enabled for customer managed keys (configurable 90–2,560 days).

6. **Cross-account access requires both sides.** Key policy in the key-owning account must allow the external account; IAM policy in the caller's account must allow the KMS actions.

7. **Encryption context is AAD — not secret, but binding.** Must match exactly during decrypt. Can appear in CloudTrail. Can be required via key policy conditions.

8. **Multi-Region keys have shared material but independent policies.** Replicating a key does not copy its policy.

9. **Deletion waiting period (7–30 days) is intentional.** After deletion, data encrypted under that key is permanently unrecoverable. There is no AWS-side recovery path.

10. **Disabling a key interrupts service immediately** but is reversible. Use this for rapid incident response before committing to deletion.

11. **AWS managed keys cannot be used cross-account.** Only customer managed keys support cross-account access via key policy.

12. **Grants are used by AWS services, not directly by end-user applications.** They allow constrained, delegated key usage without modifying the key policy.

### Common Exam Scenarios

| Scenario | Answer |
|----------|--------|
| EC2 app can't decrypt S3 objects encrypted with CMK | Check EC2 role is in key policy AllowKeyUsers statement |
| Need same encrypted data readable in two Regions | Use multi-Region keys |
| Inherited an account; can't access a KMS key | Contact AWS Support — there is no self-service recovery |
| Want to prevent a role from directly calling KMS but allow S3 SSE-KMS | Add `kms:ViaService: s3.us-east-1.amazonaws.com` condition to key policy |
| RDS snapshot shared cross-account can't be restored | RDS snapshot uses AWS managed key; share with CMK instead |
| Need to comply with BYOK requirement | Customer managed key with EXTERNAL origin (import key material) |
| Application gets `InvalidCiphertextException` on decrypt | Check encryption context — likely different on decrypt vs encrypt |
| High KMS API costs for S3 | Enable S3 Bucket Keys to reduce per-object KMS calls |
| Need to re-encrypt data without exposing plaintext in transit | Use `kms:ReEncrypt*` — decrypts and re-encrypts entirely within KMS |

### Red Flags in Exam Questions

- ❌ **"Rotate the key to fix a data breach"** → Rotation alone does not remediate; must re-encrypt data
- ❌ **"Use AWS managed key for cross-account S3 access"** → AWS managed keys cannot be used cross-account
- ❌ **"IAM policy alone is sufficient to use a KMS key"** → Key policy must also allow it (unless key policy has root trust)
- ❌ **"Deleting a key is reversible"** → After the waiting period expires, deletion is permanent
- ❌ **"Changing the alias to a new key re-encrypts existing data"** → Alias change does not touch existing ciphertext
- ❌ **"Encryption context is encrypted/hidden"** → Context is visible in CloudTrail; never put secrets in it
- ❌ **"Multi-Region key replicas share the same policy"** → Each replica has an independent key policy
- ❌ **"You can encrypt an existing unencrypted RDS instance in place"** → Must snapshot → copy encrypted → restore

## 14. Interview Questions and Answers

**Q1. What is the difference between KMS and Secrets Manager? When would you use each?**

KMS manages cryptographic keys and performs cryptographic operations (encrypt, decrypt, generate data keys). It never stores application secrets. Secrets Manager stores secret values (database passwords, API keys, OAuth tokens) and handles automatic rotation via Lambda. KMS protects Secrets Manager — it encrypts the secret at rest. Use KMS when you need to control who can decrypt data. Use Secrets Manager when you need to store, retrieve, and rotate application credentials. Both are often used together: Secrets Manager secrets are encrypted with a KMS CMK.

---

**Q2. Why use envelope encryption instead of calling KMS Encrypt for every piece of data?**

Three reasons: (1) **Size limit** — KMS Encrypt accepts at most 4 KB of plaintext. Most application data exceeds this. (2) **Performance** — Every KMS API call crosses the network to the KMS service, adding latency. Encrypting 1 GB locally with a data key is thousands of times faster than making 1 GB of KMS API calls. (3) **Cost** — KMS charges per API call. Encrypting bulk data locally with a single GenerateDataKey call instead of per-record Encrypt calls drastically reduces cost.

---

**Q3. Can an IAM administrator bypass a KMS key policy?**

No. KMS authorization always evaluates the key policy first. An IAM administrator with `AdministratorAccess` (or even `kms:*` in their IAM policy) cannot access a key unless the key policy permits it. If the key policy does not contain the root account trust statement, IAM policies have no effect at all. This is a fundamental security feature — it allows separation of cryptographic access from IAM administration.

---

**Q4. Does key rotation re-encrypt existing data?**

No. Rotation generates new key material for future encryptions. KMS retains all previous key material versions indefinitely so that existing ciphertext can still be decrypted. Existing encrypted objects in S3, EBS volumes, RDS databases, and other services are not re-encrypted. If you need to re-encrypt data (e.g., after a suspected compromise), you must explicitly re-encrypt it using `kms:ReEncrypt` or by decrypting and re-encrypting each item.

---

**Q5. What is the minimum and maximum waiting period for key deletion? Why does it exist?**

Minimum 7 days, maximum 30 days. The waiting period exists because if a key is deleted and data encrypted under it has not been re-encrypted or backed up, that data becomes permanently unrecoverable — AWS cannot retrieve deleted key material. During the waiting period, any API calls that would require the key are logged in CloudTrail, which can reveal still-in-use keys. If usage is detected, you can cancel the deletion. After the waiting period expires, the deletion is irreversible.

---

**Q6. Multi-Region keys — are the key policies shared across Regions?**

No. Key policies are independent per regional key resource. Replicating a primary key to another Region creates a replica with only the default key policy (root account trust). You must explicitly configure the replica's key policy to match your security requirements. The only things shared between a primary and its replicas are the cryptographic key material and the `mrk-` key ID prefix.

---

**Q7. How do you give Account B access to a KMS key owned by Account A?**

Two steps, both required: (1) In Account A, add a statement to the key policy granting the desired KMS actions to `arn:aws:iam::AccountB:root` (or a specific role ARN in Account B). (2) In Account B, attach an IAM policy to the role/user granting the same KMS actions on the specific key ARN from Account A. Both must allow the operation for cross-account access to succeed. Only customer managed keys support this — AWS managed keys cannot be shared cross-account.

---

**Q8. What is kms:ViaService and when would you use it?**

`kms:ViaService` is a condition key that matches when a KMS request originates from a specific AWS service. For example, `kms:ViaService: s3.us-east-1.amazonaws.com` means the request came from S3 on behalf of the principal, not from the principal making a direct KMS API call. Use it to ensure a key is only used through specific service integrations (e.g., a key is only allowed to be called via S3 SSE-KMS, not via direct application calls). This is useful when you want to enforce that encryption always happens through a specific service, preventing an application from directly calling KMS with arbitrary plaintext.

---

**Q9. How do you re-encrypt data after suspecting a key is compromised?**

You cannot simply rotate the key and consider it resolved. Steps: (1) Rotate the key on-demand to stop new encryptions from using the compromised material. (2) Audit CloudTrail to identify all resources encrypted under the compromised key material version and time window. (3) For S3 objects: use `aws s3 cp` with `--sse-kms-key-id` pointing to a new key, or use S3 Batch Operations with an inventory. (4) For database snapshots/volumes: copy with a new CMK. (5) For application-level ciphertext: call `kms:ReEncrypt` to have KMS decrypt under the old material and re-encrypt under the new material without the plaintext leaving KMS. (6) Revoke the grants and IAM permissions that allowed the compromised access path. (7) Consider disabling or deleting the old key material after all data is migrated.

---

**Q10. What is the difference between disabling a key and scheduling it for deletion?**

Disabling a key is immediately reversible — you can re-enable it with `aws kms enable-key`. It stops all encrypt/decrypt operations but preserves the key resource, its policy, and all key material. Scheduling deletion sets a waiting period (7–30 days) after which the key is permanently and irreversibly destroyed. During the waiting period, the key cannot be used for any cryptographic operations. Canceling deletion during the window restores the key to Disabled state (not Enabled — you must explicitly enable it after canceling). Use disable for incident response; use deletion only when you are certain the key is no longer needed.

---

**Q11. What happens if you accidentally lock yourself out of a KMS key?**

If you modify the key policy in a way that removes all valid principals (e.g., delete the root trust statement and the key admin role), no one in your account can view, modify, or delete the key policy. There is no self-service recovery mechanism in the KMS console or API. You must contact AWS Support, verify your identity as the account owner through the root user, and request that AWS restore the default key policy. This process is not instantaneous. Prevention: always test key policy changes in a non-production environment; retain the `EnableRootAccountPermissions` statement unless you have a deliberate, reviewed reason to remove it.

---

**Q12. An application is getting ThrottlingException from KMS. What are your options?**

In order of preference: (1) **Implement exponential backoff with jitter** in the application — transient throttles are expected. (2) **Use data key caching** (AWS Encryption SDK) — reuse a data key for a bounded number of bytes or time, reducing the number of `GenerateDataKey` calls. (3) **Enable S3 Bucket Keys** if the throttling is from S3 SSE-KMS — bucket-level data keys reduce per-object KMS calls by orders of magnitude. (4) **Review key usage** — multiple services or environments sharing one key magnify throttling; consider separate keys per workload. (5) **Request a quota increase** via AWS Service Quotas console for the specific KMS API operations being throttled.

---

**Q13. What is the difference between `GenerateDataKey` and `GenerateDataKeyWithoutPlaintext`?**

`GenerateDataKey` returns both the plaintext data key and its encrypted form. Use this when the application will immediately encrypt data with the key. `GenerateDataKeyWithoutPlaintext` returns only the encrypted data key. Use this for deferred-encryption workflows — for example, when you want to pre-generate and store encrypted data keys for resources that will be encrypted later (e.g., pre-provisioning encrypted EBS volumes). It also appears in grant operations for services like Auto Scaling, which provisions encrypted volumes without needing to decrypt immediately.
